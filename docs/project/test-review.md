# Test Review (working file)

> **Audience:** project owner, Claude Code · **Status:** working file of step 3 of [`plan.md`](plan.md) (created
> 2026-10-19). When the step ends its conclusions move to the permanent documentation (test pages, roadmap,
> design decisions, `OPEN_QUESTIONS.md`) and this file and `test-review/` are removed (git keeps them).

## Purpose

Review every implemented test and design every missing one, as if starting from a blank page: the current code is
the starting material, not a constraint. The goal is a tool whose verdicts an enterprise user can trust on any API
behind any gateway; the labs (Forgejo + Kong, crAPI + Kong, Forgejo + APISIX) prove it. crAPI is used as a
positive case for **categories** of weakness (BOLA, mass assignment, SSRF, ...): a test is designed on the
category, from what the tool knows of any API (the OpenAPI specification and `config.yaml`); nothing specific to
crAPI enters the code.

## How we work

| Phase | Content | Output |
|---|---|---|
| 0a | Rules common to every test, decided once (topics below) | a decision per topic, recorded here |
| 0b | The base: the methodology's guarantees and the roadmap, against the current standards | the revised catalogue of guarantees |
| 1 | The 18 implemented tests, one at a time | one draft per test in `test-review/` |
| 2 | The missing guarantees | one draft per test in `test-review/` |

- **Draft:** `test-review/<id>.md` (e.g. `test-review/2-1.md`) is the future test page (template below) followed
  by a review box. It replaces the page in `docs/tests/` only when the code is written and verified on the labs:
  until then the test pages describe what the code does today.
- **Review box:** problems found (with the evidence: code line, lab run), research (sources), options considered
  and the recommendation, the owner's decision, the changes (code, configuration, documentation, labs), done when.
- **Rules:** facts verified against the code, a run or a cited source; proposals marked as such; one topic or test
  at a time; the owner decides and closes questions.
- **Files that follow a test** (besides its page): [`roadmap.md`](roadmap.md), the "Test portability" table of
  [`compatibility.md`](../reference/compatibility.md#test-portability),
  [`assessment-model.md`](../architecture/assessment-model.md), the usage guides
  ([`read-the-report.md`](../guides/usage/read-the-report.md),
  [`configure-a-target.md`](../guides/usage/configure-a-target.md),
  [`select-tests.md`](../guides/usage/select-tests.md)), `CHANGELOG.md`; generated by `hatch run dev:gen`: the
  catalogue, the page header, the parameter tables, `config.example.yaml`.

## Page template

Proposed 2026-10-19; to confirm in phase 0a. Compared with the current pages (sections: what it checks, how it
works, outcomes, oracle states, prerequisites and effects, configuration, coverage against the methodology, why it
exists, limitations) and with how two scanners document a check: Burp (severity and confidence certain / firm /
tentative, issue background, remediation) and ZAP (risk, confidence, solution, references, CWE, payload and
evidence per alert).

| # | Section | Content |
|---|---|---|
| - | Generated header | ID, name, domain, priority and strategy, CWE, tags, needs, parameters (as today) |
| 1 | Guarantee | what a PASS promises and what it does not; the threat; the OWASP category |
| 2 | Coverage of the methodology | each sub-test: implemented, partial, or left out with the reason |
| 3 | Inputs | the specification fields, the configuration keys, the gateway concepts it reads |
| 4 | Preconditions and positive controls | what must hold to give a verdict, how the test checks it, what happens otherwise |
| 5 | Probes | the requests, their number, their order (destructive ones last) |
| 6 | Oracle | decision table per response: violation, enforced, inconclusive; calibration |
| 7 | Outcomes | PASS / FAIL / SKIP / ERROR; how the inconclusive part is shown |
| 8 | Findings | title, content, confidence, the evidence it points to |
| 9 | Effects on the target | what it creates or changes, cleanup, safe in production or not, interference with other tests |
| 10 | Per gateway | Kong, APISIX, others |
| 11 | Configuration | parameters and examples |
| 12 | Validation | expected verdict on each lab with its basis; secure and vulnerable variant; the crAPI case of the category |
| 13 | Remediation | what to do on FAIL (gateway, application) |
| 14 | Limitations | what the test cannot detect |
| 15 | Sources | methodology, OWASP, ASVS, RFCs, gateway documentation |

## Phase 0a: topics

In this order; each ends with the owner's decision, written under it.

1. **Calibration and gateway recognition** (A4, A5, B1).
2. **Positive controls** of credentials and objects (B2, B3).
3. **Response classification**: a shared vocabulary of outcomes, inconclusive answers made visible, transport errors
   recorded (A6, A8, C3).
4. **Inputs from the specification versus configuration**: endpoint selection and sampling, knowledge derived from
   the spec (A7, B5).
5. **Findings**: evidence (Q-50), confidence, the severity rule of the external tests (C1, C2).
6. **Effects on the target, order, interference** (Q-30, C4).
7. **Shared capabilities to build and where they live**: normalization, HSTS and debug paths written once (A1-A3),
   login artefacts (B4), out-of-band listener (B6), new gateway concepts and empirical confirmation (B7, B8), the
   unused helpers (B9), credential placement in probes (C5).
8. **Standards and references**: which standards, which versions, the reference format.
9. **Validation on the labs**: secure and vulnerable variants, the crAPI categories, the tests that SKIP on every
   lab (0.3, 1.6) (Q-51).
10. **The page template** above.
